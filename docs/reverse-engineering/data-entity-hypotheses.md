# VRSOC Phase 00 — Data Entity Hypotheses

This document maps all observed data concepts to relational entity models for the target PostgreSQL/Supabase backend.

---

## 1. Entity Models & Classification

### 1.1 `organizations` & `memberships` (Multi-Tenancy Foundation)
- **OBSERVED**: Base44 user profile loads via `/entities/User/me`.
- **INFERRED**: Multi-tenant SaaS requires top-level organization boundary for data ownership.
- **UNKNOWN**: How Base44 partitions client workspaces internally.
- **TARGET**:
  - `organizations` table (`id`, `name`, `slug`, `created_at`).
  - `organization_members` table (`id`, `organization_id`, `user_id`, `role`, `joined_at`).
  - Strict RLS: `organization_id = auth.current_organization_id()`.

### 1.2 `agents` (EDR Fleet)
- **OBSERVED**: Hostname, IP address, OS, Agent version, CPU/RAM/Disk metrics, Last seen, Status (`online`, `offline`, `warning`, `critical`).
- **INFERRED**: Agent heartbeat updates telemetry every 10-60 seconds.
- **TARGET**:
  - `agents` table (`id`, `organization_id`, `hostname`, `ip_address`, `os`, `os_version`, `agent_version`, `status`, `cpu_usage`, `ram_usage`, `disk_usage`, `last_heartbeat_at`, `created_at`).

### 1.3 `alerts`
- **OBSERVED**: Title, Severity (`critical`, `high`, `medium`, `low`), Risk score (`0-100`), Category, MITRE Tactic/Technique, Asset, Source IP, User, Status (`open`, `acknowledged`, `closed`, `false_positive`), Description.
- **INFERRED**: Generated by correlation detection rules firing on telemetry logs.
- **TARGET**:
  - `alerts` table (`id`, `organization_id`, `title`, `severity`, `risk_score`, `category`, `mitre_tactic_id`, `mitre_technique_id`, `asset_id`, `source_ip`, `username`, `status`, `description`, `raw_event_payload`, `assigned_to`, `created_at`, `updated_at`).

### 1.4 `incidents` & `cases`
- **OBSERVED**: Incident number, title, severity, priority (`P1`-`P4`), status (`detection`, `analysis`, `containment`, `eradication`, `recovery`, `lessons_learned`, `closed`), analyst notes, lead responder.
- **INFERRED**: An incident represents an active security event; a case represents the full dossier including evidence, IOCs, and analyst notes.
- **TARGET**:
  - `incidents` table (`id`, `organization_id`, `incident_number`, `title`, `severity`, `priority`, `status`, `lead_analyst_id`, `declared_at`, `closed_at`).
  - `case_notes` table (`id`, `incident_id`, `author_id`, `note_text`, `created_at`).
  - `case_evidence` table (`id`, `incident_id`, `evidence_type`, `file_url`, `ioc_value`, `added_at`).

### 1.5 `soar_playbooks` & `soar_executions`
- **OBSERVED**: Playbook name, category, description, trigger condition, actions list, status (`active`, `draft`), execution history (`duration`, `result`, `approvals`).
- **INFERRED**: Stored as JSON graph workflows.
- **TARGET**:
  - `soar_playbooks` table (`id`, `organization_id`, `name`, `category`, `description`, `workflow_nodes_json`, `status`, `created_at`).
  - `soar_executions` table (`id`, `playbook_id`, `incident_id`, `status`, `logs_json`, `duration_ms`, `executed_at`).
  - `soar_approvals` table (`id`, `execution_id`, `action_name`, `status`, `requested_by`, `approved_by`, `comment`, `created_at`).

### 1.6 `telemetry_logs` (SIEM Ingestion)
- **OBSERVED**: Timestamp, log source, host, severity, raw message, parsed JSON fields.
- **INFERRED**: High-volume append-only event stream.
- **TARGET**:
  - `telemetry_logs` table (`id`, `organization_id`, `timestamp`, `source_type`, `host`, `severity`, `event_type`, `raw_message`, `normalized_json`).

### 1.7 `knowledge_articles`
- **OBSERVED**: Title, category, difficulty (`beginner`, `intermediate`, `advanced`), content markdown, tags.
- **TARGET**:
  - `knowledge_articles` table (`id`, `title`, `category`, `difficulty`, `content_md`, `is_published`, `order_index`).
